# ClipDis v1.1.0 Multi-Watch-Folder Design

Status: **Unreleased / implementation in progress**

This document records the product requirements, design decisions, persistence changes, safety rules, implementation state, and verification requirements for the ClipDis v1.1.0 multi-watch-folder feature.

It intentionally distinguishes what is already implemented on the feature branch from work that still requires QML/GuiBridge integration and Windows verification.

## 1. Problem in v1.0.0

ClipDis v1.0.0 has one configured watch folder and one separately configured uploaded/archive folder. Valorant metadata is controlled by one global enable flag. Discord message content has no per-source caption model.

That model becomes ambiguous when a user records multiple games into different folders. A second watch folder needs its own archive destination, metadata behavior, display identity, and optional caption without creating multiple competing ClipDis worker pipelines.

## 2. Product goals

v1.1.0 must provide:

- one or more watch folders;
- no user-selected uploaded/archive path;
- one app-owned archive folder per watch root;
- the ability to open each watch root and each corresponding archive;
- clear-one and clear-all archive operations;
- per-watch-folder Valorant rank/level enablement;
- per-watch-folder optional custom Discord caption;
- source-profile identity on clips shown by the UI;
- dashboard filtering by watch-folder profile;
- automatic migration from v1.0.0 configuration;
- preservation of v1.0.0 media/state safety invariants.

## 3. Watch-folder profile model

A watch folder is no longer modeled as only a path string. It is a persistent profile:

```text
WatchFolderProfile
  id: stable UUID string
  name: user-facing friendly name
  path: normalized watch root
  show_valorant_stats: bool
  caption_enabled: bool
  caption_text: string
```

The UUID is the logical identity. The path is mutable profile data.

Renaming/reordering profiles must not create a new logical source identity.

Current implementation: `app/config.py`.

## 4. Config schema v2

`AppConfig` now contains:

```text
config_version = 2
watch_folders = [WatchFolderProfile, ...]
```

The old fields `watch_folder`, `uploaded_folder`, and `use_henrik_stats` are temporarily retained as compatibility mirrors while old call sites/QML are converted. New subsystem logic must use `watch_folders`.

The existing persistence namespace remains:

```text
%APPDATA%\ValorantClipUploader
```

This is deliberate backward compatibility and is not part of the v1.1 rename/migration work.

## 5. v1.0.0 migration

When `config.json` predates schema v2 or contains a legacy `watch_folder` without v2 profiles:

1. copy the current config once to `config.v1.backup.json`;
2. create exactly one watch-folder profile;
3. assign a UUID;
4. use the legacy watch root as the profile path;
5. use the watch-root basename as the default profile name;
6. migrate legacy `use_henrik_stats` to `show_valorant_stats`;
7. default caption settings off/empty;
8. write schema v2.

Migration is idempotent. Subsequent loads reuse the stored UUID and must not duplicate profiles.

The legacy configured uploaded folder is historical user data. ClipDis v1.1.0 does not delete, clear, move, or silently import its contents.

## 6. Derived archive path

Each profile owns exactly one derived archive folder:

```text
<watch root>\ClipDis Uploaded
```

The fixed directory name is:

```text
ClipDis Uploaded
```

It is not user-configurable in v1.1.0.

Reasons:

- removes setup friction;
- keeps each game's archive adjacent to its source clips;
- makes archive ownership unambiguous;
- allows profile-ID-scoped clear/open operations;
- clearly marks the directory as app-owned rather than a generic user folder.

Current implementation: `profile_uploaded_folder()` in `app/config.py` and profile-aware archiving in `app/archive.py`.

## 7. Critical scanner exclusion

Because `ClipDis Uploaded` now lives inside the watched tree, recursive scanning must never enter it.

This is a hard safety invariant for v1.1.0:

```text
A file under <watch root>\ClipDis Uploaded must never become a ClipDis job.
```

The worker uses an `os.walk` traversal that prunes the archive directory before candidate discovery. This is stronger than checking filenames after discovery because archived media never reaches the normal file-ready/job-creation path.

Current implementation: `_iter_files(watch_folder, archive_folder)` in `app/worker.py`.

Regression test: `test_archive_subtree_is_pruned_before_discovery`.

## 8. Multiple-root ownership rules

Watch roots must be unique and non-overlapping.

Rejected examples:

```text
C:\Clips
C:\Clips
```

and:

```text
C:\Clips
C:\Clips\Valorant
```

and the reverse parent/child order.

Reason: a physical clip must have one unambiguous owning profile. Allowing overlapping roots would create duplicate discovery and inconsistent caption/archive/stat behavior.

Current implementation: `validate_watch_folders()` in `app/config.py` and `WatchFolderService.add_profile/update_profile`.

## 9. One global worker

Multiple profiles do not create one FFmpeg worker per profile.

ClipDis retains one global `ClipWorker` and existing global locks for processing, uploading, archiving, exact selected-job execution, and Auto Upload cycles.

The watcher iterates profiles and aggregates discoveries, but queued media continues through the existing bounded global pipeline.

Reasons:

- avoids simultaneous unbounded encodes;
- preserves gaming/system responsiveness;
- preserves existing retry/failure protections;
- avoids duplicate ownership/state-machine complexity.

Current implementation: `app/worker.py`.

## 10. Missing profile behavior

A missing watch path affects only that profile.

If at least one profile exists and is available, the worker continues scanning valid profiles. Worker status reports per-profile availability and a missing-profile count.

If all profiles are missing, watching is unavailable until at least one root returns.

A single missing folder is not a whole-application fatal error.

## 11. Durable SQLite ownership

The `jobs` table gains:

```text
watch_folder_id TEXT
watch_folder_path TEXT
```

`watch_folder_id` is the stable logical owner.

`watch_folder_path` is a source-root snapshot for diagnostics/history.

Existing databases are migrated with additive `ALTER TABLE` logic. Existing job statuses/archive paths are preserved.

When a legacy job has no profile ID and its source path maps unambiguously to one current profile, ownership may be backfilled. Ambiguous historical data must not be guessed.

Current implementation: `app/state.py`.

## 12. Profile removal safety

Removing a profile removes configuration only. It never deletes the watch directory, archive directory, or historical jobs.

Removal is blocked while the profile owns an active or failed job. Failed jobs are included because the user may retry them later; removing ownership would make retry/archive behavior ambiguous.

Completed history may retain a profile UUID/path snapshot after the profile is removed.

Current implementation: `WatchFolderService.remove_profile()`.

## 13. Archive routing

Archiving remains downstream of confirmed Discord success.

For an uploaded job:

```text
job.watch_folder_id
→ current owning profile
→ profile path
→ profile path\ClipDis Uploaded
→ collision-safe move
```

For legacy jobs without an ID, a source-path fallback is accepted only if it maps to exactly one configured profile.

If no owner can be resolved, archiving fails safely and the original remains where it is.

The v1.0.0 invariant remains unchanged:

```text
Never move/delete the original clip before confirmed Discord upload success.
```

Current implementation: `app/archive.py`.

## 14. Per-profile Valorant metadata

Riot/Henrik credentials remain global:

```text
riot_username
riot_tagline
valorant_region
Henrik API key secret
```

Each watch-folder profile controls:

```text
show_valorant_stats
```

For a processed job, ClipDis resolves the owning profile before deciding whether to contact Henrik.

If the profile toggle is off, no Henrik request is performed for that upload.

If enabled and Henrik fails, the clip upload still proceeds with an unavailable-stats message, preserving the existing optional-integration behavior.

Current implementation: `app/discord_uploader.py`.

## 15. Per-profile captions

Each profile controls:

```text
caption_enabled
caption_text
```

Caption limit at the profile layer:

```text
1800 characters
```

Discord final content limit:

```text
2000 characters
```

When caption and stats are both present:

```text
<caption>

Rank: **...**
Level: **...**
```

When both sections are disabled/empty, the file can be sent with no unnecessary content.

Current implementation: `build_webhook_payload()` in `app/discord_uploader.py`.

## 16. Discord mention safety

Caption text is user-controlled and must not unexpectedly ping Discord users/roles.

Multipart webhook uploads use `payload_json` and include:

```json
{
  "allowed_mentions": {
    "parse": []
  }
}
```

Therefore text such as `@everyone` remains visible text without generating a broad mention through ClipDis's webhook payload.

Current implementation: `upload_file_to_webhook()`.

## 17. Profile-scoped archive maintenance

The backend exposes profile-ID-scoped behavior through `app/watch_folders.py`.

Implemented service operations:

```text
get_profiles
add_profile
update_profile
remove_profile
open_paths
ensure_uploaded_folder
preview_clear_uploaded
clear_uploaded
preview_clear_all_uploaded
clear_all_uploaded
```

The destructive methods do not accept a raw path from the UI. They accept a profile ID and derive the expected archive path in Python.

## 18. Clear-operation safety model

Before reading/deleting an archive, ClipDis verifies that the path is exactly the expected `ClipDis Uploaded` child of the profile root.

The archive directory itself must be an ordinary directory rather than a symlink/reparse-point redirect.

Clear operations delete only safe regular top-level files. Unexpected directories, links, reparse points, or unreadable entries are skipped and reported.

ClipDis does not recursively erase unexpected directory trees.

The empty `ClipDis Uploaded` directory is retained.

Preview data includes:

```text
profile ID/name
archive path
file count
total bytes
unexpected entry count/list
```

Clear results include:

```text
deleted
skipped
failed
bytesFreed
```

This backend contract is intended to support explicit QML confirmations with correct scope and size information.

## 19. Planned UI information architecture

The backend is implemented first so QML can bind to stable profile APIs rather than becoming the data model.

The intended UI is:

### Settings

Visible Watch Folders list/cards, not one ComboBox hiding the configurations.

Each profile should expose:

```text
name
short path
missing/available state
Valorant Stats on/off
Caption on/off
Open
Edit
Remove
```

The edit surface should show the derived archive path read-only and expose profile caption/stat toggles.

Global Discord credentials, FFmpeg status, startup, Riot identity, region, and Henrik key remain outside profile-specific cards.

### Dashboard

Use a compact filter ComboBox for the single current filter:

```text
All Folders
<profile 1>
<profile 2>
...
```

This is distinct from profile management. The list is used for managing multiple entities; the ComboBox is used for one filtering choice.

Clip cards should display the owning profile's friendly name rather than a long path.

### Quick actions

Menus/dropdowns are appropriate for commands such as:

```text
Open Folders
  Profile A / Open Watch
  Profile A / Open Uploaded
  Profile B / Open Watch
  Profile B / Open Uploaded
```

and:

```text
Clear Uploaded
  Profile A...
  Profile B...
  Clear All...
```

### Confirmation dialogs

Destructive dialogs should state exact scope, count, size, and path rather than generic Yes/No wording.

Example:

```text
Clear uploaded clips from "Rocket League"?

18 archived clips (2.4 GB) will be permanently deleted from:
D:\Clips\Rocket League\ClipDis Uploaded

[Cancel] [Clear uploaded clips]
```

The destructive action should not receive unsafe default focus.

- expose global Valorant credentials separately from per-profile enable toggles;
- add dashboard source-profile labels;
- add dashboard profile filtering;
- ensure Select All applies to visible filtered clips only;
- add Open Folders quick action;
- add Clear Uploaded per-profile/all menu;
- bind clear previews into explicit confirmation dialogs;
- update diagnostics for profile lists;
- run source tests/smoke checks;
- run QML smoke checks;
- build debug and release onedir packages;
- run the actual Windows GUI with computer use;
- test two isolated temporary roots;
- visually inspect normal/minimum window sizes;

- synchronize final source/Vault documentation after verified behavior.

## 23. Release status

Do not publish or tag v1.1.0 from the current implementation-progress state.

The public release remains v1.0.0 until the UI integration, local packaged-build tests, computer-use verification, final documentation synchronization, and release QA are complete.
