# ClipDis v1.1.0 Multi-Watch-Folder Design

Status: **Published — v1.1.0, September 14, 2026**

Release tag: `v1.1.0`

Release source commit: `8affaab92a10932808bc37bee537eb631335b3bd`

Release asset: `ClipDis-v1.1.0-windows-x64.zip`

SHA-256: `150ba3612d03638cbe969c2053254172bd71c46bcccb0128db724df4d3c55d45`

This document records the product requirements, architecture, design decisions, migration behavior, safety rules, user-interface model, implementation contracts and final verification for the ClipDis v1.1.0 multi-watch-folder release.

## 1. Problem in v1.0.0

ClipDis v1.0.0 has one configured watch folder and one separately configured uploaded/archive folder. Valorant metadata is controlled by one global enable flag. Discord message content has no per-source caption model.

That becomes ambiguous when a user records multiple games into different folders. Each source needs its own archive destination, metadata behavior, display identity and optional caption without creating multiple competing ClipDis processing pipelines.

## 2. Product goals delivered in v1.1.0

v1.1.0 provides:

- one or more watch folders;
- no user-selected uploaded/archive path;
- one app-owned archive folder per watch root;
- the ability to open each watch root and its corresponding archive;
- clear-one and clear-all archive operations;
- per-watch-folder Valorant rank/level enablement;
- per-watch-folder optional custom Discord caption;
- source-profile identity on dashboard clips;
- dashboard filtering by watch-folder profile;
- exact Select All Visible behavior under filtering;
- automatic migration from v1.0.0 configuration;
- preservation of v1.0.0 media/state safety invariants.

## 3. Watch-folder profile model

A watch folder is a persistent profile rather than only a path string:

```text
WatchFolderProfile
  id: stable UUID string
  name: user-facing friendly name
  path: normalized watch root
  show_valorant_stats: bool
  caption_enabled: bool
  caption_text: string
```

The UUID is the logical identity. The path and friendly name are profile data.

Renaming or reordering profiles does not create a new logical source identity.

Implementation: `app/config.py`.

## 4. Config schema v2

`AppConfig` contains:

```text
config_version = 2
watch_folders = [WatchFolderProfile, ...]
```

Legacy fields such as `watch_folder`, `uploaded_folder`, and `use_henrik_stats` remain only at compatibility boundaries. v1.1 profile-aware runtime/UI behavior uses `watch_folders` as the source of truth.

The existing persistence namespace intentionally remains:

```text
%APPDATA%\ValorantClipUploader
```

Changing that directory in the same release would have risked appearing to erase existing user configuration/state.

## 5. v1.0.0 migration

When `config.json` predates schema v2 or contains a legacy `watch_folder` without v2 profiles:

1. copy the existing config once to `config.v1.backup.json`;
2. create exactly one watch-folder profile;
3. assign a UUID;
4. use the legacy watch root as the profile path;
5. use the watch-root basename as the default profile name;
6. migrate legacy `use_henrik_stats` to `show_valorant_stats`;
7. default caption settings to off/empty;
8. write schema v2.

Migration is idempotent. Reloading the migrated config reuses the stored UUID and does not duplicate the profile.

The legacy configured uploaded folder is treated as historical user data. v1.1.0 does not delete, clear, move or silently import its contents.

## 6. Derived archive path

Each profile owns exactly one derived archive folder:

```text
<watch root>\ClipDis Uploaded
```

The directory name is fixed in v1.1.0:

```text
ClipDis Uploaded
```

It is not user-configurable.

Reasons:

- removes a setup field;
- keeps each game's archive adjacent to its source clips;
- makes archive ownership unambiguous;
- enables profile-ID-scoped open/clear operations;
- clearly marks the directory as app-owned rather than a generic user directory.

Implementation: `profile_uploaded_folder()` in `app/config.py`, `app/archive.py`, and `app/watch_folders.py`.

## 7. Critical scanner exclusion

Because `ClipDis Uploaded` lives inside the watched tree, recursive scanning must never enter it.

Hard invariant:

```text
A file under <watch root>\ClipDis Uploaded must never become a new ClipDis job.
```

The worker uses an `os.walk` traversal that prunes the archive directory before candidate discovery. This prevents already-uploaded media from reaching normal file-ready/job-creation logic.

Implementation: `_iter_files(watch_folder, archive_folder)` in `app/worker.py`.

Regression coverage verifies both direct and nested files under the archive subtree are excluded.

## 8. Multiple-root ownership rules

Watch roots must be unique and non-overlapping.

Rejected duplicate:

```text
C:\Clips
C:\Clips
```

Rejected parent/child pair:

```text
C:\Clips
C:\Clips\Valorant
```

The reverse ordering is rejected as well.

Reason: a physical clip must have one unambiguous owning profile. Overlapping roots could cause duplicate discovery and inconsistent caption/archive/stat behavior.

Implementation: `validate_watch_folders()` and `WatchFolderService.add_profile/update_profile`.

## 9. One global worker

Multiple profiles do not create one permanent FFmpeg worker per profile.

ClipDis retains one global `ClipWorker` and existing global locks for:

- processing;
- uploading;
- archiving;
- exact selected-job execution;
- Auto Upload cycles.

The watcher iterates profiles and aggregates discoveries, but queued media continues through the bounded global pipeline.

Reasons:

- avoids simultaneous unbounded encodes;
- preserves gaming/system responsiveness;
- preserves existing retry/failure protections;
- avoids duplicate ownership/state-machine complexity.

## 10. Missing profile behavior

A missing watch path affects only that profile.

If at least one profile exists and is available, ClipDis continues scanning valid profiles. Worker status reports per-profile availability and a missing-profile count.

If all profiles are missing, watching remains unavailable until a root returns.

One missing game directory is not treated as a whole-application fatal condition.

## 11. Durable SQLite ownership

The `jobs` table adds:

```text
watch_folder_id TEXT
watch_folder_path TEXT
```

`watch_folder_id` is the stable logical owner.

`watch_folder_path` is the source-root snapshot useful for diagnostics/history.

Existing databases are migrated additively. Existing job status/history/archive values are preserved.

A legacy job without a profile ID may be backfilled only when its source path maps unambiguously to one current profile.

Implementation: `app/state.py`.

## 12. Profile removal and path-change safety

Removing a profile removes configuration only. It does not delete the watch directory, archive directory or historical jobs.

Removal is blocked while the profile owns unresolved work, including active and failed jobs. Uploaded-but-not-yet-archived work also retains ownership requirements.

Equivalent unresolved-job checks protect profile path changes where changing ownership context could make pending work ambiguous.

Completed historical jobs may retain a profile UUID/path snapshot after the profile configuration is removed.

## 13. Archive routing

Archiving remains downstream of confirmed Discord success.

```text
job.watch_folder_id
→ owning profile
→ profile path
→ profile path\ClipDis Uploaded
→ collision-safe move
```

For legacy jobs without an ID, source-path fallback is accepted only when it maps to exactly one configured profile.

If no owner can be resolved, archiving fails safely and the original remains in place.

The v1.0.0 invariant remains unchanged:

```text
Never move/delete the original clip before confirmed Discord upload success.
```

Filename-collision handling remains preserved.

## 14. Per-profile Valorant metadata

Riot/Henrik identity remains global:

```text
riot_username
riot_tagline
valorant_region
Henrik API key secret
```

Each profile controls:

```text
show_valorant_stats
```

For a processed job, ClipDis resolves the owning profile before deciding whether to contact Henrik.

If the profile toggle is off, no Henrik request is made for that upload.

If enabled and Henrik fails, the clip upload is still allowed to proceed because metadata is optional.

The global Valorant credential test can force a test request without mutating any profile's toggle.

## 15. Per-profile captions

Each profile controls:

```text
caption_enabled
caption_text
```

Profile caption limit:

```text
1800 characters
```

Discord final content limit:

```text
2000 characters
```

When caption and stats are both present:

```text
<caption>

Rank: **...**
Level: **...**
```

When both sections are disabled/empty, ClipDis sends the attachment without unnecessary content.

## 16. Discord mention safety

Caption text is user-controlled and must not unexpectedly ping Discord users/roles.

Multipart webhook uploads use `payload_json` with:

```json
{
  "allowed_mentions": {
    "parse": []
  }
}
```

Text such as `@everyone` therefore remains visible text rather than producing a broad mention through ClipDis.

## 17. Profile-scoped archive maintenance

`app/watch_folders.py` exposes profile-ID-scoped service behavior:

```text
get_profiles
add_profile
update_profile
remove_profile
open_paths
ensure_uploaded_folder
preview_clear_uploaded
clear_uploaded
preview_clear_all_uploaded
clear_all_uploaded
```

Destructive methods do not accept an arbitrary raw path from QML. They accept a stable profile ID and derive the expected archive path in Python.

## 18. Clear-operation safety model

Before reading/deleting an archive, ClipDis verifies that the path is exactly the expected `ClipDis Uploaded` child of the profile root.

The archive itself must be an ordinary directory rather than a symlink/reparse-point redirect.

Clear operations delete only safe regular top-level files. Unexpected directories, links, reparse points or unreadable entries are skipped/reported.

ClipDis does not recursively erase unexpected directory trees.

The empty `ClipDis Uploaded` directory is retained.

Preview data includes:

```text
profile ID/name
archive path
file count
total bytes
unexpected entry count/list
```

Clear results include:

```text
deleted
skipped
failed
bytesFreed
```

## 19. Final UI information architecture

### Settings

Persistent profiles are managed through a visible Watch Folders list/card surface rather than hiding all profiles inside one ComboBox.

Each profile exposes:

```text
name
short path
missing/available state
Valorant Stats on/off
Caption on/off
Open
Edit
Remove
```

The edit surface shows the derived archive path read-only and exposes profile caption/stat settings.

Discord credentials, FFmpeg status, startup, Riot identity, region and Henrik API key remain global.

### Dashboard

A compact profile filter provides:

```text
All Folders
<profile 1>
<profile 2>
...
```

Filtering uses stable profile IDs, not friendly names.

Clip cards/details expose the source profile's friendly name.

`Select All` under a profile filter is exact **Select All Visible** behavior: hidden clips are not silently included in selected upload/delete operations.

### Folder quick actions

Dashboard actions provide profile-aware access to:

```text
Open Watch
Open Uploaded
```

Opening an Uploaded folder creates the derived archive when needed.

### Clear Uploaded actions

Users can choose one profile or Clear All.

Every destructive action first requests backend preview data and displays explicit scope, count, size and path information.

Example:

```text
Clear uploaded clips from "Rocket League"?

18 archived clips (2.4 GB) will be permanently deleted from:
D:\Clips\Rocket League\ClipDis Uploaded

The Discord uploads are not affected.

[Cancel] [Clear uploaded clips]
```

The destructive button uses explicit wording and does not receive unsafe default focus.

### Empty and missing states

The UI explicitly handles:

- no profiles configured;
- one/many profiles;
- one profile missing while others remain available;
- all profiles missing;
- no clips;
- no clips under the selected filter;
- archive absent/empty;
- caption disabled/enabled;
- optional Valorant credentials.

## 23. Packaging and icon verification

The release remains PyInstaller **onedir**:

```text
ClipDis.exe
_internal/
```

`_internal` is required and contains Qt/QML runtime payloads, app GUI resources and bundled FFmpeg/ffprobe.

The application icon has multiple layers of protection:

1. `ClipDis.spec` embeds `app/gui/assets/app_icon.ico` into `ClipDis.exe`.
2. `app_icon.ico` and `app_icon.png` remain inside packaged GUI assets.
3. Runtime Qt sets the application/window/tray icon.
4. Windows AppUserModelID remains `Hermann.ClipDis`.
5. The final release workflow parses the built PE and requires an `RT_GROUP_ICON` resource before publication.

The release workflow also rejects the incompatible host-PATH `icu*.dll` packaging regression.

## 25. Known follow-up items

These are not blockers to the published v1.1.0 artifact, but remain useful future work:

- the app is unsigned, so Windows SmartScreen/unknown-publisher warnings remain possible;
- installer/signing/uninstall cleanup are not implemented;
- `%APPDATA%\ValorantClipUploader` remains intentionally unchanged for compatibility;
- legacy config mirror fields can be revisited in a later cleanup cycle;
- additional interactive clean-machine tray/startup QA would improve coverage;
- the user's pre-existing normal AppData `state.db` was found corrupt during QA and intentionally left untouched to avoid destroying history;
- a live clip upload to a confirmed disposable Discord channel remains a useful final integration exercise, although webhook validation and mocked multipart upload behavior passed.

## 26. Release status

**v1.1.0 is published and is the current public ClipDis release.**

The release tag is intentionally immutable from this point forward. Future fixes should use a new patch version such as `v1.1.1`; future backward-compatible features should use an appropriate minor version.
